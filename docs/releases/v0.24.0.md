# v0.24.0

## Offline candidate rechecks and vulnerability explanations

v0.23.0 introduced offline scanning with prepared databases. In this release, `suggest_fix` and `explain_vulnerability` also work offline, using the same local databases and without any network request.

- **`suggest_fix` candidate rechecks**: each recommended version is rechecked against the local databases. Every version is scanned by the native offline matcher as a private single-component SBOM. The result is `candidate_check_source: "local_database"`. If a candidate turns out to be affected by an advisory that the project scan did not report, another version is selected, as with the online recheck. Every candidate scan must use the same database digest and download timestamp as the project scan. Missing, invalid, expired or changed databases, unidentified candidates and incomplete scanner output fail the request instead of returning `clean`. There is no fallback to the API. `clean` describes only the local snapshot
- **`explain_vulnerability`**: searches canonical IDs and direct aliases, such as a CVE ID for a GHSA record, in every prepared database. It reads verified private copies of the database ZIPs and does not extract entries or run OSV-Scanner. The result adds `requested_id`, `matched_by` (`id` or `alias`), `matching_record_ids`, `offline_database` and, when several records match, `related_records`. A local miss returns `vulnerability_not_found` for the prepared snapshots only. It does not mean the ID is absent from OSV or that a package is safe
- **Limits**: one lookup reads every record of every prepared database. The limits are 4 MiB per record, 2 GiB of expanded data, 500,000 entries and 120 seconds. Exceeding them returns `output_too_large` or a timeout, never a partial result. With the complete npm database (232,645 records) prepared, one lookup took about 20–24 seconds in our measurements. Local lookups share the concurrency limit of native scans (2 by default)
- **Fix since the first implementation**: the official npm database contains four records whose aliases are not OSV IDs, such as trailing commas and SNYK IDs over 64 characters. These are now accepted as data. Before the fix, every offline explanation failed while the npm database was prepared. Requested IDs are still validated before any database access

See the README section "Offline mode and database preparation", `docs/OFFLINE_VALIDATION.md` and `docs/OFFLINE_NPM_VALIDATION.md`.

## Development

- The repository's own CI dependency scan has a temporary exception in `osv-scanner.toml`, with a reason and an expiry date. It covers `picomatch` 4.0.7 (GHSA-fc5q-39xc-vjpf, ReDoS), which reaches the project only through the development dependency `vitest`. No fixed release exists yet. The scan reports it again when the exception expires on 2026-12-18. This advisory does not affect the published package. `picomatch` is not installed with `osv-scanner-mcp`, and `npm audit --omit=dev` reports no findings
- Research validation records in `docs/validation` bind the exact `package.json` and `package-lock.json` bytes they were measured with. The version bump in this release makes them differ at HEAD again, as described for v0.23.0

## Verification

- Automated tests (product scope: 3,161 passed), type check and build
- **Offline**, with the real OSV-Scanner 2.7.0 under an OS network-deny profile on macOS arm64:
  - **Go** (official complete database, `docs/validation/offline-candidates-2026-11-18.json` and `offline-explanations-2026-11-18.json`): candidate rechecks with four synthetic alias controls, ID/alias explanations and the invalid-database refusals
  - **Maven** (`docs/validation/offline-maven-2026-11-18.json`): `log4j-core` 2.14.1 workflows
  - **npm** (complete official database, `docs/validation/offline-npm-2026-11-18.json`): `lodash` 4.17.20 found 4 advisories. The initial candidate 4.18.0 was rejected by a newly found advisory, and 4.18.1 was selected and rechecked as clean. GHSA and CVE lookups returned the same record, and 40 invalid-database cases were refused. No Node network request was made
- **Packed package** (`docs/OFFLINE_PACKAGE_VALIDATION.md`): offline `npm ci` into an empty directory on Node 22.13.0, 24.22.1 and 26.12.1, with the MCP tool calls repeated on each. Node 20.19.6 is refused with `EBADENGINE`. These records were measured with version 0.23.0 sources and the same offline code
- Dependency audit: `npm audit --omit=dev` reports no findings. On `package-lock.json`, OSV-Scanner 2.7.0 reports no findings apart from the excepted development-only `picomatch` advisory above
