# v0.6.0

## `suggest_fix` Now Supports Python (PyPI)

`suggest_fix` recommends upgrade versions for PyPI packages, in addition to Maven, npm, and Go.

- **Version comparison** follows PEP 440, with the same normalization and ordering as PyPA `packaging`: epochs, pre-releases (`a`, `b`, `rc`, and spellings such as `c`, `alpha`, `-rc0`), post-releases, dev releases, and local versions. Non-canonical values in advisories, such as `1.8c1` (Django) and `2.8.0-rc0` (TensorFlow), are normalized. The implementation was checked against `packaging` 26.2 on 20,000 randomly generated comparisons.
- **Upgrade tiers** use the same rule as npm and Go: a minor update within 0.x is `cross_major`, because some 0.x packages (such as FastAPI) make breaking changes in minor releases. A change of epoch is also `cross_major`. Post-releases count as stable; `rc` and `dev` versions count as pre-releases and are recommended only when no stable candidate fixes every vulnerability.
- **Commit-based (`GIT`) ranges** are ignored when the same entry also has an `ECOSYSTEM` range. Entries with only `GIT` ranges are still treated as incomplete.
- **Lower bounds**: `requirements.txt` lines with `>=X` or `~=X` are scanned at their lower bound X. These suggestions are marked `version_is_lower_bound: true`, and the note explains that the recommendation means raising the lower bound, since the installed version may differ.
- **Update hints** for PyPI: update the specifier in `requirements.txt`, `pyproject.toml`, or `Pipfile` and regenerate the lockfile; for transitive dependencies, use a pip constraints file (`-c`) or the override settings of uv or Poetry.
- Package names are matched with PEP 503 normalization.

Examples verified with osv-scanner and live OSV data: requests 2.19.0 → 2.33.0, urllib3 1.23 → 2.8.0, Jinja2 2.10 → 3.1.6, Django 3.2.0 → 5.2.17, FastAPI 0.65.0 → 0.109.1 (`cross_major`).

## Fix: Unsorted Range Events Withheld Recommendations

The OSV format does not require the events in a range to be sorted; evaluation sorts them. Some advisories (for example many PYSEC records) list several intervals in one range in a different order, such as `introduced 2.0.0, fixed 2.0.6, introduced 0, fixed 1.26.17`. Earlier versions treated this as malformed data and withheld the recommendation. Events are now sorted by version before evaluation, in every ecosystem. Ranges that still do not alternate between a start and an end after sorting (overlapping intervals, or an end without a start) remain treated as incomplete. Recommendations that were previously withheld for this reason may now be given; other Maven, npm, and Go results are unchanged.

## Other Changes

- Values in an advisory's `versions` list that cannot be parsed as versions (such as Git tag names like `nightly-binary`) are ignored instead of making the data incomplete. This list is only used to check whether a candidate equals an affected version, and an unparseable value cannot equal a valid candidate. This applies to all ecosystems.
- `fixed_versions` for PyPI in `scan_project` and `scan_sbom` is now sorted by PEP 440 precedence (previously in the order listed by OSV).

## Known Limitation

A recommended version can be affected by vulnerabilities that were introduced after the current version and therefore do not appear in the scan. For example, cryptography 3.2 is recommended 49.0.0, which is affected by two vulnerabilities introduced in 44.0.0 and fixed in 50.0.0. Checking candidates against the OSV database is planned.
