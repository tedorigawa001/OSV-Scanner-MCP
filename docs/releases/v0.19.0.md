# v0.19.0

## Direct and transitive dependencies for Composer

Composer packages now have `dependency_relation`, `declared_in`, and `introduced_by` in `scan_project` and `suggest_fix` (until v0.18.0 they were always `unknown`).

- **Direct dependencies** are the packages in `require` and `require-dev` of the `composer.json` next to the `composer.lock`. They have `declared_in` with that `composer.json` (relative to the project)
- **Transitive dependencies** are found by following each locked package's `require`. They have `introduced_by` with the direct dependencies they come through (up to 10, with the rest counted in `introduced_by_omitted`). A package that is both declared directly and required by another dependency is `direct` and also has `introduced_by`
- Platform requirements (`php`, `ext-*`, `lib-*`) are not dependencies. `require-dev` of dependencies, `suggest`, and `conflict` are not followed
- **Nothing is guessed.** Duplicate package names, names that are ambiguous because of `provide` or `replace`, virtual packages, and packages that cannot be reached from `composer.json` are `unknown`. This is reachability over the locked packages, not a constraint solver: it does not check whether `composer.lock` is up to date or matches `composer.json`
- Local `path` packages are followed as links in the graph (a package they require can show the local package in `introduced_by`), but they are still neither scanned nor sent. Path repository URLs and the packages' own files are never read
- If the `composer.json` is missing, cannot be read (4 MiB limit), or cannot be interpreted, or the analysis reaches its limit (2,000,000 steps shared by all Composer files in a scan), the relations are `unknown` and `coverage.composer_warnings` says so. The lockfile is still scanned

`suggest_fix` uses the relations in its `update_hint`: for a direct dependency, update the constraint in the `composer.json` listed in `declared_in`; for a transitive dependency, update the direct dependencies in `introduced_by` or their constraints. Regenerate `composer.lock` in a trusted environment with scripts and plugins disabled.

Checked through MCP with the real OSV-Scanner 2.7.0: `symfony/http-kernel` (in `require`) is `direct` with `declared_in: ["composer.json"]`, `symfony/http-foundation` (required by `http-kernel`) is `transitive` with `introduced_by: ["symfony/http-kernel"]`, and a package in `require-dev` that a local path package also requires is `direct` with `introduced_by` naming the local package.

## Verification

- Automated tests (1065), type check, and build
- Through MCP with the real OSV-Scanner 2.7.0: the relations above, with recommendations (`symfony/http-kernel` → 5.4.20, `symfony/http-foundation` → 5.4.50)
- Hostile dependency graphs: a 20,000-package chain and 1,500 packages that all require each other (2.25 million edges) stop at the limit in under 0.3 seconds and are reported as `unknown`; a 300-package project with 60 direct dependencies is analyzed in 2 ms
- Dependency audit (`npm audit` and OSV-Scanner): no findings; dependencies are unchanged since v0.18.0

npm publication is separate from this GitHub release.
