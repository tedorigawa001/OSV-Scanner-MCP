# v0.10.0

## `scan_java_artifact`: Inferred Coordinates Are Now Flagged

Testing with real artifacts (Spring Boot fat JARs, Jenkins WARs, and shaded JARs from Maven Central) showed that for JARs without `pom.properties` — including the main Spring Framework JARs — osv-scanner infers Maven coordinates from file names and often gets the groupId wrong (for example `spring-beans:spring-beans` instead of `org.springframework:spring-beans`). Vulnerabilities are not matched for wrong coordinates, so they were silently missed. For example, Spring4Shell (CVE-2022-22965) in spring-beans 5.3.2 inside zipkin-server 2.23.2 was not detected.

- Coordinates whose groupId contains no `.` are treated as inferred. They are listed in `coverage.inferred_coordinates` (count, items, and a warning), and the affected packages are marked `coordinates_inferred: true`. Correct old-style coordinates such as `commons-io:commons-io` are included as well, erring on the safe side. Wrong inferences that contain a `.` cannot be detected.
- An archive identified only through inferred coordinates now has the status `inferred_only`, even when vulnerabilities were found for it (its `identified_vulnerability_count` still shows them, but other vulnerabilities may be missed). It is not counted in `jars_identified` and is listed in `unidentified_jars` with a hint. Previously, shaded JARs without metadata (such as grpc-netty-shaded 1.84.1) were reported as identified with no known vulnerabilities.
- Coordinates found in `pom.properties` were all detected in these tests, including in shaded JARs that keep the metadata. For accurate results, scan the build's lockfile or `pom.xml` with `scan_project`.

## Smaller Responses

Responses from `scan_project`, `scan_java_project`, `scan_java_artifact`, and `scan_sbom` no longer contain `affected_versions`, the internal affected-range data used to verify `suggest_fix` recommendations. It made up about 90% of large responses (a Jenkins WAR scan shrank from about 1.3 MB to 59 KB). Recommendations are unchanged.

## Running Under Node's Permission Model

The server can run under Node's permission model (`node --permission ...`) as an optional extra layer of defense. The README has a new section, "権限を絞って起動する", with a configuration example.

- When the permission model denies access, every tool now returns the new error `permission_denied`, naming the missing permission and the path. Previously this appeared as `project_not_found`, `sbom_not_found`, `binary_not_found`, or `internal_error`, and a denied subdirectory was silently skipped during the directory search.
- If a required permission is missing (the temporary directory under both its symlinked and resolved paths, child processes, `OSV_MCP_ALLOWED_ROOT`, `OSV_SCANNER_PATH`, or the download cache), the server prints a warning to stderr at startup.
- osv-scanner runs as a child process and is not restricted by Node's permission model.

npm publication is separate from this GitHub release.
