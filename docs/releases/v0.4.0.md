# v0.4.0

## New Tool: `scan_project` (Java / JavaScript / Python / Go)

`scan_project` detects lockfiles and manifests in a project and scans them together. Package managers and builds are never run.

| Ecosystem | Files |
|---|---|
| Java (Maven) | `pom.xml`, `gradle.lockfile`, `buildscript-gradle.lockfile` |
| JavaScript (npm) | `package-lock.json`, `npm-shrinkwrap.json`, `yarn.lock`, `pnpm-lock.yaml`, `bun.lock` |
| Python (PyPI) | `poetry.lock`, `uv.lock`, `Pipfile.lock`, `pdm.lock`, `requirements*.txt` |
| Go | `go.mod` |

The response starts with a `coverage` section that lists what could not be scanned: manifests without a lockfile (`lockfile_missing`, with `status: "missing"` or `"unconfirmed"` and steps to generate one), requirements lines without a pinned version (`unpinned_requirements`), lines that are not scanned (`unscannable_requirements`, with a reason), and excluded files (`skipped_files`). When anything is missing, `coverage.complete` is `false` and a warning states that zero findings does not mean the project is safe.

`requirements.txt` files are not passed to osv-scanner. The server parses them and scans a private temporary copy that contains only the dependency lines it could interpret, rewritten to a simple form such as `name==version`. The copy contains no include directives or options. osv-scanner interprets include directives on its own (it follows `- r ../x.txt`, with a space, as an include), so any difference between the two parsers could otherwise be used to read files outside the scanned directory. Includes (`-r`, `--requirement`) that stay inside the project directory are expanded by the server. Lines using `>=` or `~=` are scanned at their lower bound, as osv-scanner does, and the affected packages are marked `version_is_lower_bound: true`.

Fix suggestions (`suggest_fix`) remain Java-only in this release.

## Security Fix: Parent POMs Outside the Allowed Root Were Read

Affected versions: v0.3.4 and earlier. Fixed in v0.4.0.

osv-scanner reads the parent POM referenced by `<parent>` in a `pom.xml` (the file at `<relativePath>`, or `../pom.xml` when omitted) and follows the chain to grandparents, adding the dependencies declared there to the results. This happens even with `--no-resolve`. In v0.3.4 and earlier, a `pom.xml` inside `OSV_MCP_ALLOWED_ROOT` could reference a parent POM outside it, and that file's dependencies were included in the results and sent to the vulnerability lookup.

When `OSV_MCP_ALLOWED_ROOT` is set, v0.4.0 excludes any `pom.xml` whose parent POM chain references a file outside the allowed root. Parent POMs inside the allowed root are still read, so scanning a submodule continues to work. GAV matching is not checked; an outside reference that exists is excluded to stay on the safe side.

The parent reference is read the way osv-scanner's XML decoder reads it: elements are matched by local name regardless of namespace prefix (`<m:parent>` counts as a parent), only a `parent` directly under the root element is used, and character references are expanded. A `pom.xml` is also excluded when its parent reference cannot be interpreted with certainty, for example duplicate `parent` or `relativePath` elements, CDATA, a DOCTYPE, unknown entities, property references, unclosed tags, or content that is not valid UTF-8.

## Behavior Changes

- `scan_java_project` and `suggest_fix` add `skipped_manifests` and `scope_warning` to the response, before the counts, when a `pom.xml` is excluded for the reason above. These fields are not present otherwise, so existing responses are unchanged. If every manifest is excluded, or the excluded `pom.xml` was specified directly, the tools return `path_outside_allowed_root`.
- Packages may include `dependency_groups` (for example `dev`) when osv-scanner provides it. This value is missing or inaccurate for some lockfile formats and should be treated as informational. Maven results do not include it, so Java responses are unchanged.
