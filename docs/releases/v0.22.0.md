# v0.22.0

## Breaking change: Node.js 22.13 or newer

Node.js 20 reached end of life on 2026-04-30 and is no longer supported. The package now requires Node.js 22.13 or newer, the first Node 22 release with the stable `--permission` model described in the README. CI tests Node 22, 24 and 26.

## Where dependencies come from: Pipenv

`scan_project` and `suggest_fix` now report `dependency_relation`, `declared_in` and `introduced_by` for `Pipfile.lock` (spec 6), and check child projects against it.

- **Direct dependencies** are the registry releases declared in the captured root `Pipfile`: `packages` maps to the locked `default` category, `dev-packages` to `develop`, and custom categories keep their names. `declared_in` names the `Pipfile`
- **Transitive dependencies**: `Pipfile.lock` has no dependency edges. Other locked registry entries are `transitive` only in a category whose declarations all match locked entries and that has at least one root. `introduced_by` is given only when every category that locks the release without declaring it has exactly one possible origin. Otherwise it is omitted rather than reported partially
- **Child coverage**: a child `pyproject.toml` under a parent `Pipfile.lock` is confirmed only when a root `Pipfile` path declaration and a unique locked entry agree on its exact relative directory and package name, and all its static runtime requirements are locked at compatible releases in the same category. Markers, extras, dynamic metadata, non-empty optional or development groups and legacy backends stay `unconfirmed`
- **Custom categories are scanned.** OSV-Scanner reads only `default` and `develop`, so non-empty custom categories are also scanned as separate temporary copies
- Pipenv, Python, plugins and build backends are never run. Local, Git and URL entries are not treated as registry releases, and source paths are never followed to read files. `Pipfile.lock` is read with strict JSON parsing (duplicate keys and nesting above 128 are rejected), up to 16 MiB per file and 64 MiB in total. Companion files are read up to 4 MiB each

## Gradle: dependency graphs, origins and declaration sources (source checkout)

Gradle projects with `gradle.lockfile` can now report direct/transitive relations, `introduced_by` and, with explicit opt-in, `declared_in`. The server never launches Gradle, the Wrapper or a JVM. It reads only a companion file that you generate in a trusted build environment, and the companion is never sent to OSV.

- **Dependency graph (Stage A/B)**: `gradle/export-dependency-graph.init.gradle`, shipped in the npm package, writes `osv-mcp-gradle-dependencies.json`. It requires Gradle 8.11 or newer (verified with 8.11.1 and 9.2.1 on JDK 21) and supports Groovy and Kotlin builds. Relations follow the selected component and variant edges, and constraints are excluded from dependency paths. `coverage.dependency_metadata.gradle` reports companion paths, configurations, completeness and diagnostic reasons. Settings and build-file inputs are captured before evaluation and verified, so stale metadata is reported. A newer schema version is reported as `unsupported_schema_version`, separately from invalid metadata
- **Declaration sources (C1a, C1b)**: with `OSV_MCP_GRADLE_DECLARATION_TRUST=registered-helper-v1`, author-attested declaration maps written by `gradle/register-declarations.init.gradle` supply `declared_in`. Synchronous module declarations (C1a) and `Provider` declarations (C1b) are supported. Unregistered additions suppress the whole declaration list for that scope instead of reporting part of it
- **Version catalogs and `ProviderConvertible`**: with `OSV_MCP_GRADLE_CATALOG_TRUST=local-catalog-inputs-v1` as well, catalog aliases and bundles can be declaration sources
- **Convention plugins**: with `OSV_MCP_GRADLE_PLUGIN_TRUST` and approved toolchain profiles (`OSV_MCP_GRADLE_PLUGIN_TOOLCHAIN_PROFILES`, and `OSV_MCP_GRADLE_PLUGIN_LOADER_PROFILES` for the loader-attested policy), explicitly registered local `buildSrc` and included-build convention plugins can be declaration sources. `gradle/plugin-provenance.init.gradle` records them. Precompiled Kotlin, standard `kotlin-dsl`, published plugins, the configuration cache and parallel export are not supported. See `docs/GRADLE_CONVENTION_PLUGIN_USAGE.md`
- **Verified relations are kept when trust is not available.** An unknown trust value, an unsupported catalog model or an unapproved plugin profile withholds only the declaration sources and adds a reason to the Gradle metadata. The server keeps running, and verified relations and `introduced_by` are still reported. Trust settings are read once at startup
- Update hints in `suggest_fix` name verified declaration paths when available, and otherwise refer to the applicable Gradle declarations or constraints
- Ordinary default project locks are the supported scope. Buildscript locks, custom lock locations, included/composite builds and Android-specific layouts need further validation

### Experimental: owned BTA diagnostic

A companion with `schemaVersion: 4` can carry experimental owned-manifest metadata next to the ordinary graph. The ordinary graph is validated exactly as before. The owned part is checked for structure only and reported in `coverage.dependency_metadata.gradle[].owned_manifest`. This is an experimental diagnostic, not a supported feature. It is disabled by default (`OSV_MCP_GRADLE_OWNED_BTA_TRUST`, `OSV_MCP_GRADLE_OWNED_BTA_PROFILES`). This release ships no approved profile and no isolated authority backend, so owned files are never read and no owned diagnostic result is produced.

Research on Kotlin compiler plugin inputs, owned build inputs and independent provider planning (the C3b and CPR experiments in `docs/GRADLE_KOTLIN_PLUGIN_DECLARATIONS.md`) continues as research and validation work. It is not part of the server's behavior in this release. Some of its modules are included in the package but are not used by the server.

## Fixes

- When the same package is found in several lockfiles, `introduced_by` is now omitted if any file that does not report it as direct cannot name its origin. Before, the origins of the other files were returned as if they were complete
- `declared_in` is now omitted when any source has an incomplete declaration list, instead of listing only part of the declaring files
- For npm direct dependencies whose declaring `package.json` is not confirmed, the update hint no longer names the root `package.json`
