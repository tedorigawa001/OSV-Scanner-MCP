# v0.23.0

## Offline scanning with prepared databases

The server can now scan without network access, using complete public OSV ecosystem databases that you prepare in advance. Online scanning remains the default; offline mode is used only when you enable it.

- **Preparation**: on a connected machine, `node dist/index.js cache --ecosystems npm,PyPI --directory /absolute/offline-cache` downloads the official `all.zip` of each selected ecosystem from `https://osv-vulnerabilities.storage.googleapis.com`. It reads no project files and sends no package names or versions. Supported databases: `Maven`, `npm`, `PyPI`, `Go`, `crates.io`, `Packagist` and `NuGet`. Refresh with the same command. Databases that are not selected stay as they were, and a failed refresh keeps the previous manifest
- **Scanning**: set `OSV_MCP_OFFLINE=1` and `OSV_MCP_OFFLINE_DB_DIR` (absolute path). `scan_project`, `scan_java_project`, `scan_java_artifact`, `scan_sbom` and the scanning part of `suggest_fix` use the local databases, and responses include `offline_database` with download timestamps, SHA-256 digests and a snapshot warning. Databases older than `OSV_MCP_OFFLINE_MAX_AGE_HOURS` (default 168, 1–720) are refused
- **Fails closed**: missing, unreadable, expired, future-dated or corrupted cache data fails the scan instead of returning a clean result. Each scan uses verified private copies of the databases, so a concurrent refresh cannot change the bytes it reads
- **No network fallback**: offline mode disables deps.dev resolution, the OSV API, and the automatic OSV-Scanner download. A checksum-verified cached binary can be reused, or set `OSV_SCANNER_PATH`. Preparation is refused while offline mode is enabled
- **Not available offline in this release**: `explain_vulnerability` returns an error instead of contacting the API. `suggest_fix` computes recommendations from the scanned affected ranges, but does not recheck candidates against the API or the local databases. `candidate_check` is `disabled` with an explanation. Project lockfiles with Git/VCS references are refused, because the offline matcher cannot verify commits
- **Storage**: database ZIPs are limited to 512 MiB each, and the object cache to 2 GiB and 128 objects. Each refresh removes objects that the selected manifest no longer references, so the cache keeps at most the selected and the new generation. A per-scan private snapshot may use up to 2 GiB of temporary space

See the README section "Offline mode and database preparation" and `docs/OFFLINE_VALIDATION.md`.

## Research (not part of the server's behavior)

Gradle E2-P0 backend research (static contracts, codecs and local durable storage, §9.162–9.164 of `docs/GRADLE_KOTLIN_PLUGIN_DECLARATIONS.md`) continues as research and validation work. Some of its modules are included in the package but are not used by the server.

## Development: product and research test scopes

`npm test`, which `prepublishOnly` runs, now covers only the product. Research tests, including the reproduction of the research validation records in `docs/validation`, run with `npm run test:research`. Those records bind the exact `package.json` and `package-lock.json` bytes and their own verification code, so they verify against the commit they were measured at, and fail at a later commit after a version bump or dependency update. `scripts/run-tests.mjs` decides the scope of each test file from its imports and the evidence it reads, and `node scripts/run-tests.mjs --list` prints both scopes. The real-time process diagnostics CI job runs from the research scope.

## Verification

- Automated tests, type check, and build
- **Offline**, with the real OSV-Scanner 2.7.0 and the complete official Go database under an OS network-deny profile on macOS (recorded in `docs/validation/offline-2026-11-16.json`): `scan_project` and `scan_sbom` found 5 vulnerabilities in `golang.org/x/text` 0.3.0, `suggest_fix` recommended 0.41.0 with the candidate check disabled, `explain_vulnerability` was refused, and missing, expired and corrupt caches were rejected. No Node network request was made. Other ecosystems and the refresh object collection are covered by automated tests with small fixtures, not by complete native databases
- Dependency audit (`npm audit` and OSV-Scanner 2.7.0 on `package-lock.json`): no findings

npm publication is separate from this GitHub release.
