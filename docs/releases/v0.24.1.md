# v0.24.1

## Security Fixes

Affected versions: v0.24.0 and earlier. Each parser was affected from the release that introduced it. Fixed in v0.24.1.

### A crafted manifest could stall the server

Several parsers of scanned project files used regular expressions whose backtracking grew quadratically with the input, and cubically in one case. A running regular expression cannot be interrupted, so the scan timeout did not apply, and the server stopped answering all tool calls until it finished. Scanning a single malicious repository was enough. No data was read outside the scan scope and no code was executed.

- **`pom.xml` `<relativePath>`**: a long run of whitespace inside the value took about 4 seconds at 100 KB. At the 10 MiB file limit it would take hours. Surrounding whitespace is now removed without a regular expression, with the same result.
- **`requirements.txt`**: lines are split only at `\n`, so a lone `\r` or U+2028/U+2029 could remain inside a line and make each match fail and backtrack. A 100 KB line took seconds, and a line at the 1 MiB file limit would take minutes. The patterns now treat these characters like any other character.
- **`go.mod`, `Cargo.lock`/`Cargo.toml` and Classic `yarn.lock`**: the same characters after a long run of whitespace took about 3–4 seconds at 100 KB. The whitespace is now read without backtracking. Matches and the values read are unchanged.
- **`pdm.lock`**: an editable (`-e`) requirement took about 12 seconds at 4,000 characters, growing cubically up to the 16,384-character limit. Requirements containing line terminators are no longer interpreted. PDM does not write them.

## Behavior Changes

- In `requirements.txt`, a comment (`#` at the start of a line or after whitespace) is now removed even when a lone `\r` follows it. Previously such a line was reported as a line that cannot be interpreted.
- In `pdm.lock`, a requirement containing `\n`, `\r`, U+2028 or U+2029 is treated as unsupported. Known declarations are kept, as for other unsupported requirements.

Scanning behavior, responses and the pinned OSV-Scanner 2.7.0 are otherwise unchanged from v0.24.0.

## Development

- Research validation records in `docs/validation` bind the exact `package.json` and `package-lock.json` bytes they were measured with. The version bump in this release makes them differ at HEAD again, as described for v0.23.0

## Verification

- Automated tests (product scope: 3,174 passed), type check and build. 13 new regression tests use crafted inputs. With reduced input sizes, 7 of them fail on the previous code at about 4 seconds each, and the `pdm.lock` case takes 4.4 seconds at 3,000 characters
- Dependency audit: `npm audit` and OSV-Scanner 2.7.0 on `package-lock.json` report no findings
- GitHub Actions passed on Node.js 22, 24 and 26 on Linux, macOS and Windows, including the OSV-Scanner job

npm publication is separate from this GitHub release.
