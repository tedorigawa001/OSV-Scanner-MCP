# v0.17.0

## PHP (Composer) support in `scan_project` and `suggest_fix`

`scan_project` and `suggest_fix` now scan `composer.lock`, including both `packages` and `packages-dev`, as Packagist packages. Pass a project directory, `composer.lock`, or `composer.json`. Neither Composer nor PHP code is run.

**`composer.lock` is not passed to OSV-Scanner as it is.** The server reads it safely and scans a private copy that contains only package names and release versions. Repository URLs, dist/source references and commit IDs, scripts, and credentials never reach OSV-Scanner.

- **Your own packages are not looked up.** Entries with `dist.type: "path"` (packages from a path repository, such as the packages of a monorepo) are local code. OSV-Scanner alone looks them up as Packagist packages, so a local package with the same name and version as a vulnerable public package was reported as vulnerable, and internal package names were sent to `api.osv.dev`. They are now excluded and counted in the new `coverage.local_composer_packages`; like `local_crates` and `local_projects`, they do not make `coverage.complete` false (their own dependencies are listed in `composer.lock` and scanned)
- **Only release versions are looked up.** Branch and dev versions (`dev-main`, `1.x-dev`), aliases, and other formats are not evaluated. They are listed in `skipped_files` with the reason, and `coverage.complete` is false
- **Package origin.** A lockfile cannot prove where a package came from, so the names and versions of private packages (other than path packages) are sent to `api.osv.dev` as well, and a private package with the same name as a public one can produce a false positive. When entries lack Packagist's standard notification URL, `coverage.composer_warnings` says so; it is a heuristic, not proof of origin
- A `composer.json` without a `composer.lock` in the same directory is listed in `coverage.lockfile_missing`. A lockfile in a parent directory does not establish coverage for an independent child project. `vendor` directories are not searched
- Limits: 16 MiB per lockfile and 64 MiB per scan, with the same JSON structure checks as npm lockfiles. Invalid JSON excludes only that file
- `dependency_relation` is `unknown` for Composer packages. Development packages are marked `dependency_groups: ["dev"]` by OSV-Scanner

**Recommendations.** `suggest_fix` compares Composer versions with one to four numeric components, an optional `v` prefix, and alpha / beta / RC / stable / patch suffixes (including their short forms), following Composer's ordering. An advisory whose version boundaries cannot be compared does not produce a verified fix. Upgrade tiers follow the existing cautious rules (a minor update within 0.x is `cross_major`). `update_hint` explains how to update the constraints in `composer.json` and regenerate `composer.lock` in a trusted environment. Check PHP and extension requirements first. `fixed_versions` for Packagist are sorted by Composer ordering.

The behavior was checked against real lockfiles from public repositories (phpmyadmin/phpmyadmin, matomo-org/matomo, firefly-iii/firefly-iii): the packages scanned are exactly the ones OSV-Scanner reads from the original files, except the branch versions that are deliberately skipped (4 and 1), and the findings are identical.

## Verification

- Automated tests (1000), type check, and build
- Through MCP with the real OSV-Scanner 2.7.0 and 2.4.0: the sanitized copy, `packages-dev`, `v`-prefixed versions (the same OSV results as without the prefix), path packages with public names, and `suggest_fix` recommendations (for example `symfony/http-kernel` v5.4.1 → 5.4.20)
- Dependency audit (`npm audit` and OSV-Scanner) and checks with hostile input: version strings up to the 256-character limit, very long package names, 150,000 packages, and malformed entries are processed in linear time, and a malformed lockfile excludes only that file

npm publication is separate from this GitHub release.
