# v0.20.0

## Where dependencies come from: NuGet, pnpm, and Yarn

`scan_project` and `suggest_fix` now report `dependency_relation`, `declared_in`, and `introduced_by` for more formats. `declared_in` names the manifest that declares a direct dependency; `introduced_by` lists the direct dependencies a transitive one comes through (up to 10, with the rest counted in `introduced_by_omitted`). A package that is both declared directly and required by another dependency is `direct` and also has `introduced_by`. `suggest_fix` uses them in its `update_hint`.

- **NuGet**: `introduced_by` follows the dependency graph of each locked target framework (`packages.lock.json`) or target (`project.assets.json`, `*.deps.json`) separately, starting from the direct packages; origins are merged only for the same package and version. `declared_in` names the project file when exactly one captured project has an unconditional `PackageReference` for the package. `packages.config` and standalone build outputs are not guessed, and paths in restore files are never followed
- **pnpm** (`pnpm-lock.yaml` formats 5.3, 5.4, 6.0 and 9.0): importer `dependencies`, `devDependencies` and `optionalDependencies` are direct, with the importer's `package.json` in `declared_in` (as recorded in the lockfile). Peer-context-specific snapshots, npm aliases, scoped packages, cycles and several origins are supported
- **Yarn** (Classic v1 and Berry, metadata versions 4/5/6/8): Classic uses the captured root and workspace `package.json` files; Berry uses the locked `workspace:` entries. `dependencies` and `optionalDependencies` are followed
- **Nothing is guessed.** Local, link, Git, patch, portal and virtual references, ambiguous names, and packages that cannot be reached from a root are `unknown`. pnpm, Yarn, NuGet restore and MSBuild are never run, and links and source paths are never followed. This is reachability over the locked packages, not a check that the lockfile is up to date

## Workspace coverage for pnpm and Yarn

A child `package.json` with no lockfile of its own was always reported in `coverage.lockfile_missing` as `unconfirmed` when the lockfile was in a parent directory. It is now checked against that lockfile:

- **pnpm**: the child's directory must match an `importers` key exactly (after normalization; Unicode and spaces are supported)
- **Yarn Classic**: the root `package.json` must be `private` and its `workspaces` (or `workspaces.packages`) must include the child, and the child's dependencies must be in the lockfile (or be another workspace whose version satisfies the requested range). `*`, `?`, whole-segment `**`, exclusions (`!`) and one trailing `/` are supported; braces, extglobs and character classes are `unconfirmed`
- **Yarn Berry**: the child's directory must match a locked `workspace:` entry, and its declared dependencies must agree with that entry

A confirmed child is no longer listed, so `coverage.complete` can now be `true` for these workspaces. A child that is not included is `missing`; one that cannot be checked is still `unconfirmed`. **Behavior change**: in a Yarn project, a nested `package.json` that is not a workspace (for example a test fixture) is now `missing` instead of `unconfirmed`.

## Limits and safety

- pnpm and Yarn lockfiles are read once, within the selected scan directory, and the same captured bytes are used for coverage, relations and scanning. **Behavior change**: `pnpm-lock.yaml` and `yarn.lock` files over 16 MiB (64 MiB in total), or that cannot be read safely, are now skipped with a reason in `skipped_files` (and `coverage.complete` is `false`) instead of being passed to OSV-Scanner directly. Yarn `package.json` files are read up to 4 MiB each
- YAML is read from its syntax tree in linear time (a 28,000-package, 5.5 MiB lockfile takes about a second). Anchors, aliases, tags, several documents, duplicate keys and deep nesting are rejected; the relations are then `unknown` and scanning continues. **Behavior change**: `pnpm-lock.yaml` files with YAML tags such as `!!str` no longer get relations
- Each format's analysis has a 2,000,000-operation budget shared by all its files in a scan. Coverage checks and relation analysis use separate budgets, so a large monorepo that exceeds the relation budget keeps its coverage result
- New runtime dependency: `semver` (for Yarn Classic workspace ranges)

## Verification

- Automated tests (1198), type check, and build
- Through MCP with the real OSV-Scanner 2.7.0:
  - **NuGet**: lock, assets, deps and direct-reference-only projects. `Newtonsoft.Json` 12.0.1 has `introduced_by: ["Newtonsoft.Json.Bson"]` and `System.Net.Http` 4.3.0 has `declared_in`; the recommendations (13.0.1, 4.3.4) are clean
  - **pnpm**: workspaces generated by pnpm 7, 8 and 9 (formats 5.4, 6.0 and 9.0). `express` 4.17.1 and `lodash` 4.17.20 are `direct` from `package.json`, `minimist` 1.2.5 from `apps/web/package.json`, and `qs` 6.7.0 is `transitive` with `introduced_by: ["express"]`. Coverage is `complete: true`, or `missing` when the child importer is removed
  - **Yarn**: workspaces generated by Yarn 1.22.22 and 4.9.2, with included, missing and uncheckable children (12 runs), with the same relations as pnpm. The recommendations (`express` 4.20.0, `lodash` 4.18.0, `minimist` 1.2.6, `qs` 6.16.0) are clean
- Large inputs: a 5,000-package Yarn lockfile with 500 direct dependencies exceeds the relation budget in 0.4 seconds; relations are `unknown` and the workspace stays covered
- Dependency audit (`npm audit`): no findings
