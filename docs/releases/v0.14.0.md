# v0.14.0

## OSV-Scanner 2.7.0

The pinned OSV-Scanner is updated from 2.4.0 to **2.7.0**. The checksums of all six release binaries were checked against both the release's `osv-scanner_SHA256SUMS` and the digests that GitHub publishes for the release assets, and the macOS (arm64) binary was also checked after downloading it. The new binary is cached in `~/.cache/osv-scanner-mcp/v2.7.0/`; the `v2.4.0/` directory is no longer used and can be deleted.

The behaviors this server depends on were checked again with both versions side by side:

- No supported format reads files outside the scan scope through local references (same results as the earlier audit). The two known cases, `requirements.txt` includes and parent POMs, still need this server's protections, which are unchanged
- Maven properties such as `${env.X}` and `${user.home}` are not expanded, so environment values are not sent
- The `pom.xml` split between declared and resolved dependencies, the handling of `requirements.txt`, exit codes, and network destinations are unchanged
- OSV-Scanner still looks up every `Cargo.lock` package as a crates.io crate, so the crates.io-only copy remains in place
- For a project with npm, Go, PyPI, Gradle, Maven, and Rust dependencies, the `scan_project` and `suggest_fix` responses are identical to v0.13.0 with OSV-Scanner 2.4.0, as are the `scan_java_artifact` and `scan_sbom` responses for the test inputs

## `package-lock.json` entries without `resolved`

OSV-Scanner 2.7.0 treats `package-lock.json` entries without a `resolved` field as local packages and does not look them up. This would silently skip bundled dependencies (`inBundle`, or `bundled` in lockfile version 1) and registry packages in lockfiles generated with npm's `omit-lockfile-registry-resolved=true`. The private copy that is scanned now gets a public-registry URL for those entries, so they are looked up as with 2.4.0. Aliased dependencies in lockfile version 1 (`npm:<name>@<version>`, including scoped names) are filled in with the real package name and version. Links, local directories, and entries whose version is a file or git reference are left unchanged, and the original file is never modified.

## Git dependencies are sent by repository URL

Since OSV-Scanner 2.6.0, git dependencies in npm lockfiles (`package-lock.json`, `yarn.lock`, and so on) are looked up as ecosystem `GIT` using the repository URL and commit. For a private repository, its host name and path (for example `https://git.example.com/team/repo`) are sent to `api.osv.dev`. This is documented in the README, SECURITY.md, and the `scan_project` description. Git dependencies in `Cargo.lock` are still not sent.

## Fix: Cargo workspace glob matching, `[replace]` lookups, and `Cargo.lock` parsing could stall the server or exhaust memory (v0.12.0–v0.13.0)

Workspace membership checks converted `members` globs in `Cargo.toml` to regular expressions, so a crafted pattern such as `*a*a*a…*b` caused catastrophic backtracking (a regular-expression denial of service): scanning a malicious repository could stall the server. The same versions also checked each `[replace]` target in `Cargo.lock` by scanning every package, which took quadratic time (about 1.9 seconds for a 50,000-package lockfile, repeatable across several lockfiles); targets are now looked up with a single count of package identities. Globs are now matched with a bounded dynamic-programming algorithm, each check and each scan have a work limit (once the remaining limit is too small for any pattern, no further globs are examined), and members that cannot be checked within the limit are reported as `unconfirmed` in `lockfile_missing`. Literal `members` entries are looked up directly and do not count toward the limit, so large workspaces that list their members are still checked in full. The `Cargo.lock` parser no longer builds an array of all lines (a 60 MB file of blank lines used about 1.4 GB), and the number of lines (1,000,000), dependency entries (200,000), and string characters (16 Mi) is limited across the `Cargo.lock` files of a scan; a typical 400-package lockfile uses under 1% of each. Files beyond the limits are listed in `skipped_files` with the reason. In v0.13.0, mapping direct dependencies to the `Cargo.toml` that declares them also walked every crate name in the project for each `Cargo.lock`, which took time and memory proportional to the number of lockfiles times the number of crate names (900 lockfiles and 20,000 `Cargo.toml` files used about 3.6 GB); only each lockfile's own local crates are now looked up.

## Fix: Repeated `requirements.txt` include expansion could exhaust memory (v0.4.0–v0.13.0)

A shared file included with `-r` was read once and cached, but expanded again for every `requirements.txt` that included it, and the read limit did not apply to the cached text. Many `requirements.txt` files including one large file made time, memory, and the size of the scanned copies grow with the number of including files (200 files including a 950 KB file used about 1 GB of memory). Each scan now has a shared limit on the amount expanded (64 MiB) and on logical lines (100,000). Files beyond the limit are listed in `skipped_files` (or, when the limit is reached inside an include, in `unscannable_requirements`) with the reason, and `coverage.complete` is `false`.

## Fix: Parsing npm lockfiles and go.mod could exhaust resources (v0.4.0–v0.13.0)

The npm workspace check (since v0.4.0) and the direct/transitive analysis (since v0.7.0) parsed `package-lock.json` with `JSON.parse` limited only by size (64 MiB per file, 256 MiB per scan). A crafted lockfile with millions of tiny JSON values used gigabytes of memory (a 60 MB file used about 2.4 GB in the workspace check alone). JSON nesting (128 levels) and the number of structural markers (1,000,000 per file, 2,000,000 per analysis phase) are now checked before parsing, and npm lockfiles are limited to 16 MiB per file and 64 MiB per scan. When a limit is reached, workspace membership is `unconfirmed` and relations are `unknown`; a lockfile whose `resolved` fields cannot be filled in within the limits is scanned as it is and listed in `coverage.skipped_files` with the reason, so the scan is never stopped by these limits.

Since v0.7.0, the direct/transitive analysis of `go.mod` also searched every `replace` line for each required module, which took time proportional to the number of `require` lines times the number of `replace` lines (about 2.8 seconds for a 1.6 MB file with 20,000 of each). `replace` directives are now indexed by module path (0.02 seconds for the same file).

## Fix: Parent POM references could reach outside the snapshot without an allowed root (v0.4.1–v0.13.0)

Since v0.4.1, OSV-Scanner only receives private copies of the files to scan. When `OSV_MCP_ALLOWED_ROOT` was not set, however, a parent `relativePath` that climbs out of the snapshot (`../` repeated exactly up to the filesystem root, followed by an absolute path) was allowed, and OSV-Scanner then read the original file outside the snapshot, which had not been checked or copied (reproduced with OSV-Scanner 2.7.0). Such a `pom.xml` is now excluded whether or not an allowed root is set, as are parent references that cannot be interpreted and parent chains over the depth limit. After all files are copied, the parent chain that OSV-Scanner will see is checked again within the snapshot. When no allowed root is set and every file is excluded this way, the error is `no_manifest_found` (it is `path_outside_allowed_root` only when an allowed root is set).

## Fix: An empty parent `relativePath` was not followed (v0.4.0–v0.13.0)

An empty `<relativePath/>` in a `pom.xml` parent was interpreted as "no local parent", as Maven does, but OSV-Scanner (2.4.0 and 2.7.0) uses the default `../pom.xml` for it. Since v0.4.1 the snapshot then lacked that parent, so dependencies inherited from it were silently missing from the results, and the parent was not checked against `OSV_MCP_ALLOWED_ROOT`. An empty or whitespace-only `relativePath` is now treated as `../pom.xml`: the parent is copied into the snapshot when it is allowed, and a `pom.xml` whose default parent is outside the allowed root is excluded, as for other parent POMs. (In v0.4.0, which scanned the original files, this let OSV-Scanner read a parent POM outside the allowed root; v0.4.1 stopped that by scanning copies only.)

## Other Changes

- `hono` (a dependency of the MCP SDK) is updated from 4.13.7 to 4.13.13 in the lockfile, which fixes GHSA-5r4p-p66f-jhc7 (`serveStatic` path decoding). This server runs over stdio and does not use `serveStatic`
- The `--experimental-plugins` flags are kept: OSV-Scanner 2.7.0 prints a deprecation warning on stderr, but the new `--x-plugins` names are not accepted by 2.4.0, which users may still run from `PATH` or `OSV_SCANNER_PATH`
