# v0.4.1

## Security Fixes

Affected versions: v0.4.0 and earlier. Fixed in v0.4.1.

### Files could be swapped between the check and the scan

The server checked scan targets (lockfiles, `pom.xml` and its parent POM chain, JAR/WAR files) and then passed the original paths to osv-scanner. Replacing a file or a directory with a symbolic link after the check made osv-scanner read different content, including content outside the scan scope or `OSV_MCP_ALLOWED_ROOT`.

osv-scanner no longer receives any original file. The server reads each target once, safely, copies the content into a private temporary directory (owner-only, removed after the scan), and scans the copies. Checks such as the parent POM validation run on the copies, so changing the original files after the check has no effect on the results. Parent POMs are copied into the temporary directory at their original relative positions, so osv-scanner can still follow `<relativePath>` but only finds the copies that were checked. References that would climb out of the temporary directory with repeated `..` are excluded.

All reads by the server itself (lockfiles, POMs, `requirements.txt` and its includes, SBOM input) now refuse a final symbolic link, refuse anything that is not a regular file, and, after reading, re-resolve the path to confirm it is still inside the boundary and still the same file (device and inode) that was opened.

### A named pipe could stall the server

A parent POM or a `requirements.txt` include that referenced a named pipe (FIFO) caused the server to block while reading it. Files are now opened non-blocking and only regular files are read.

### A lockfile could be re-parsed many times

When checking whether `package.json` files are members of an npm workspace, the server re-read and re-parsed the same `package-lock.json` (up to 64 MiB) once per `package.json`. Each lockfile is now parsed once per scan, and the total amount the server reads for its own analysis is capped. Copies into the temporary directory are capped at 2 GiB in total; exceeding it returns the new error `scan_input_too_large`.

## Other Fixes

- An empty or whitespace-only `OSV_MCP_ALLOWED_ROOT` is now treated as unset. Previously the startup check treated it as unset, but the tools used the server's working directory as the allowed root, so every scan outside that directory failed.

## Behavior Changes

- Paths in responses (`source_files`, JAR/WAR paths) always refer to the original files; temporary paths are never returned.
- A `pom.xml` whose parent POM is a symbolic link at the final path component, or not a regular file, is scanned without that parent (osv-scanner cannot find it in the temporary directory).

npm publication is separate from this GitHub release.
