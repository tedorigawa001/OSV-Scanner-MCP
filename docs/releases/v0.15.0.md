# v0.15.0

## Scan history (opt-in)

The server can now keep a local record of scans and show what changed since the previous run. Recording is **disabled by default**, because the history keeps package names and paths on disk. Enable it with `OSV_MCP_HISTORY=1` in the server's `env`; runs are recorded from then on.

- Every run of `scan_project`, `suggest_fix`, `scan_java_project`, `scan_java_artifact`, and `scan_sbom` is recorded as one JSON file: the tool, time, duration, server and pinned OSV-Scanner versions, the target, coverage, counts, and the packages with their vulnerability IDs and aliases (and, for `suggest_fix`, the recommended versions). Vulnerability summaries, details, and error messages are not recorded. `explain_vulnerability` is not recorded
- Location: `$XDG_STATE_HOME/osv-scanner-mcp/history` (by default `~/.local/state/osv-scanner-mcp/history`), or `OSV_MCP_HISTORY_DIR`
- Retention: the latest 500 runs (`OSV_MCP_HISTORY_MAX_ENTRIES`, up to 5,000) and 100 MiB in total. Each record is kept within 1 MiB: if it would be larger, the package list is dropped (`findings_omitted`), then the manifest list is shortened (`manifests_truncated`)
- Recording never fails a scan; problems are reported as a warning on stderr

### New tool: `scan_history`

- Without arguments: the recorded runs, newest first, with time, tool, target, status, coverage, and vulnerability counts (`limit`, default 10, maximum 50)
- With `project_path`: only the runs for that target, plus `changes`, a comparison of the **last two successful runs** of each kind of scan (`scan_project` and `suggest_fix` are compared together):
  - `new_vulnerabilities` and `resolved_vulnerabilities`, compared per package (ecosystem and name). A vulnerability counts as the same if its ID or any alias matches, so a change of the primary ID in OSV is not reported as new, and a vulnerability that remains after a version change is neither new nor resolved
  - The reason for each resolved vulnerability: `version_changed` (the package is still reported, at another version), `package_not_reported` (the package is no longer in the results: upgraded to a version without known vulnerabilities, removed, or no longer scanned; scan results list only vulnerable packages, so these cannot be told apart), or `same_version_not_reported` (for example because the OSV data changed)
  - `version_changes`, with the number of vulnerabilities that remain (`still_affected`), and `coverage_changes` (`coverage.complete` and added or removed manifests)
- With `run_id`: the details of one run

Changes are computed from the OSV data at the time of each scan, so they can also appear when only the vulnerability database changed.

New error kinds: `history_disabled` (the history is not enabled), `history_unavailable` (the history directory cannot be used), and `history_run_not_found`.

### Safety

- The directory is created with mode `0700` and files with `0600`. A directory that is a symbolic link or is owned by another user is refused
- Each record is written to a temporary file and renamed, so several server processes can record at the same time
- History files are treated as untrusted input: each is read with a size limit and validated, and its strings are sanitized before being returned
- When `OSV_MCP_ALLOWED_ROOT` is set, runs whose target is outside it are not returned, and a `project_path` outside it is refused
- Under Node's permission model (`--permission`), the server warns at startup if the history is enabled but its directory cannot be read and written
- The history stays on the local machine; nothing is sent over the network

## Verification

- Automated tests (865), type check, and build
- Through MCP with the real OSV-Scanner 2.7.0: two scans of the same project before and after changing its dependencies gave the expected new and resolved vulnerabilities and version changes; with the history disabled, no directory is created and `scan_history` returns `history_disabled`
