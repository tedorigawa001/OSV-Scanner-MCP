# v0.12.0

## Rust Support in `scan_project` (`Cargo.lock`)

`scan_project` now detects and scans `Cargo.lock` (lockfile versions 1 to 4) alongside the Java, JavaScript, Python, and Go lockfiles. Cargo is never run.

### Only crates from crates.io are scanned

OSV-Scanner (v2.4.0) ignores where each package in `Cargo.lock` comes from and looks every package up as a crates.io crate. In testing, a workspace crate, a git fork, and a private-registry crate given the same names and versions as vulnerable crates.io crates were all reported as vulnerable, and their names were sent to `api.osv.dev`.

This server does not pass `Cargo.lock` to OSV-Scanner as it is. It parses the file and scans a private copy that lists only the packages whose source is crates.io (as `cargo audit` does):

- `coverage.local_crates`: the number of your own crates (workspace members and path dependencies). They are not scanned and do not make `complete` false
- `coverage.unscannable_crates`: git dependencies and crates from registries other than crates.io, with the reason. They are not scanned, so `complete` is false. Source URLs are not included in the response
- Packages replaced with `[replace]` are not scanned (they are not used); the replacement is classified by its own source
- The parser accepts only what Cargo writes. A `Cargo.lock` with anything else is excluded as a whole and listed in `skipped_files`, rather than scanned partially

Both coverage fields appear only when a `Cargo.lock` was scanned, so responses for other projects are unchanged.

### Missing lockfiles

A `Cargo.toml` without a `Cargo.lock` is listed in `coverage.lockfile_missing` with a `cargo generate-lockfile` hint (library crates often do not commit `Cargo.lock`). A workspace member is treated as covered by the root `Cargo.lock` only when the lockfile contains a local crate with its name and the root `Cargo.toml` includes the directory in `[workspace]` `members` and does not exclude it (globs with `*` and `?`). Otherwise it is `unconfirmed`. Strings and arrays in `Cargo.toml` are tracked, so settings that appear inside a multi-line string are not mistaken for real ones.

## RustSec Informational Advisories

RustSec also publishes notices that are not vulnerabilities: `unmaintained`, `unsound`, and `notice`. OSV-Scanner returns them together with vulnerabilities, and most have no fixed version. When every advisory related to a finding (including its aliases) has its details available and is such a notice, the finding is marked `informational` with its kind, listed after the vulnerabilities of the package, and counted in the new `informational_count` instead of `vulnerability_count`, `severity_breakdown`, and `vulnerable_package_count`. If another database such as GitHub's lists the same issue as a vulnerability, it stays a vulnerability.

This applies to `scan_project`, `scan_sbom`, and the per-ecosystem counts in `ecosystem_breakdown`. `informational_count` appears only when there is at least one, and `suggest_fix` does not count packages that only have such notices in `vulnerable_package_count`.

## Not Yet Supported

- `suggest_fix` returns Rust packages with `verification: "unsupported_ecosystem"` (planned for a later release, together with direct/transitive dependencies for `Cargo.lock`)
- A path dependency of a crate without `[workspace]` is reported as `unconfirmed` in `lockfile_missing`, even though it is included in the root `Cargo.lock`

## Verification

- Automated tests (632), type check, and build
- Through MCP with the real OSV-Scanner binary: lockfiles generated by Cargo 1.98 (`--offline`, nothing downloaded) with `[replace]` and with a workspace using `members` globs and `exclude`; hand-written lockfiles with local, git, and private-registry crates; and a project mixing Rust, npm, Go, PyPI, and Gradle
- Scanning `Cargo.lock` contacts only `api.osv.dev`
- For a project with npm, Go, PyPI, and Gradle lockfiles, the `scan_project` and `suggest_fix` responses are byte-for-byte identical to v0.11.0

npm publication is separate from this GitHub release.
