# v0.7.0

## Direct and Transitive Dependencies

`scan_project` and `suggest_fix` now show whether each vulnerable package is a direct or a transitive dependency. osv-scanner does not report this, so the server determines it by parsing the scanned files (the verified copies in the scan snapshot; the original files are not read again).

Each package in `scan_project` and each suggestion in `suggest_fix` has `dependency_relation`:

- `direct`: declared by the project
- `transitive`: required only through other dependencies
- `mixed`: the classification differs between lockfiles
- `unknown`: the file format is not analyzed

How it is determined:

- **`package-lock.json` / `npm-shrinkwrap.json` (lockfile version 2 and later)**: dependencies of the root and workspace `package.json` files, resolved with Node's lookup rules (nested `node_modules` first, then parent directories, following workspace links), are direct; everything reachable from them is transitive. Direct dependencies get `declared_in` (the `package.json` files that declare them, useful for workspaces). Transitive dependencies get `introduced_by` (the direct dependencies that pull them in, up to 10; the rest are counted in `introduced_by_omitted`). npm aliases (`"old-lodash": "npm:lodash@4.17.15"`) are reported under the real package name. A version that is both a direct dependency and pulled in by another dependency is `direct` and also lists `introduced_by`.
- **`go.mod`**: `require` lines without `// indirect` are direct; those with it are transitive. Modules affected by a `replace` directive get `replaced_in_go_mod: true`. A `replace` limited to a version (`replace a v1.0.0 => b v1.0.1`) is treated as applied only when the required version matches, as Go and osv-scanner do; osv-scanner reports the replacement module and version.
- **`requirements.txt`**: packages written in the file (including expanded includes) are direct; packages added by deps.dev resolution are transitive.
- **Other formats** (`pom.xml`, `gradle.lockfile`, `yarn.lock`, `pnpm-lock.yaml`, `bun.lock`, `poetry.lock`, `uv.lock`, `Pipfile.lock`, `pdm.lock`), lockfile version 1, and entries not reachable from the project are `unknown`.

`suggest_fix` uses the relation in `update_hint`: for an npm transitive dependency it names the direct dependencies to update and mentions `overrides` (effective only in the root project); for a Go module affected by `replace` it says to update the `replace` version instead of `require`; for a Go `// indirect` module it suggests `go get`; for a Python transitive dependency it suggests a constraints file or the override settings of uv or Poetry.

The analysis reads at most 256 MiB of lockfiles in total (the limit is applied before and during reading) and follows at most 2,000,000 dependency links per lockfile; files over the limits are reported as `unknown`, and the scan itself continues.

## Unchanged

- Recommended versions, notes, and per-vulnerability details in `suggest_fix` are unchanged (verified against v0.6.0 on Maven, npm, Go, and PyPI projects).
- `scan_java_project`, `scan_java_artifact`, and `scan_sbom` responses are unchanged.

npm publication is separate from this GitHub release.
