# v0.26.0

## Recovering interrupted offline database updates

Previously, a `cache` command that was killed left `update.lock` behind, and every later update was refused until the file was removed by hand. The updater now holds an OS lock on `.update.guard` (`flock` on macOS and Linux, `LockFile` on Windows), which the OS releases when the process exits.

- **Recovery**: the next `cache` command reuses an empty `update.lock` directory left by an interrupted update, removes interrupted downloads and staging manifests, and starts from the selected manifest. Leave `.update.guard` in place
- **Cleanup failures**: if a new manifest was published but cleanup failed, the command now says so instead of reporting a failed update. If the update itself failed, the original reason is kept
- **Verified**: on macOS arm64, Linux arm64 and Windows Server 2025 x64 with the CLI killed and restarted. See `docs/OFFLINE_VALIDATION.md`. A power failure or a network file system is not covered

### Before upgrading

- **`--allow-addons` on Linux**: under Node's permission model, the `cache` command now needs `--allow-addons` on Linux too, for its native lock. The MCP server itself does not. The server already needs it on macOS and Windows
- **Leftover `update.lock` file**: an older version may have left a regular file with this name. Stop all updaters, then remove it once by hand
- **Koffi on Linux**: install the optional native package for the target platform. If it cannot be loaded, `cache` refuses to update

## Less memory for offline vulnerability explanations

`explain_vulnerability` in offline mode keeps its results, ordering, limits and checks. Measured on two complete official npm databases (macOS arm64, Node.js 26.12.1, network denied):

- **Index**: heap and buffers retained after the first lookup fell from about 44 MiB to about 29 MiB. Record positions are stored in compact pages
- **Full reads**: building the index and replacing it with a new generation were faster in all three paired runs with a single prepared database, because canonical record digests are needed only to compare copies across databases. Every record is still validated
- **Hash check**: verifying the private ZIP copy reuses one 64 KiB buffer. Buffer growth during verification fell from 14–25 MiB to 0.06 MiB
- **Replacement**: the previous index is released before a new one is built. Lookups already using it finish normally

Whole-request peak memory varied between runs and still exceeds 256 MiB in some of them. See `docs/OFFLINE_NPM_VALIDATION.md` for all results.

Online behavior, scanning, `suggest_fix`, the pinned OSV-Scanner 2.7.0 and the runtime dependencies are unchanged from v0.25.0.

## Development

- Offline package installation was validated on Linux arm64 and x64 (x64 under emulation) with the published 0.25.0 tarball and the checkout before this version bump, on Node.js 22.13.0, 24.18.0 and 26.12.1. These runs did not execute `cache` or load Koffi. This release's own tarball was not run through that procedure. See `docs/OFFLINE_PACKAGE_VALIDATION.md`

- vitest 5.1.1 and related development dependencies
- Research validation records in `docs/validation` bind the exact `package.json` and `package-lock.json` bytes they were measured with. The version bump in this release makes them differ at HEAD again, as described for v0.23.0
