# v0.25.0

## Faster offline vulnerability explanations

In offline mode, `explain_vulnerability` previously read every record of every prepared database on each lookup. With the complete npm database prepared, each lookup took about 20–30 seconds. The server now keeps an in-memory index of record IDs and direct aliases for the current database generation.

- **Building the index**: the first completed lookup for a database generation still validates the entire archive set and builds the index from the validated records. The generation is identified by the cache directory and the ordered ecosystems, download timestamps and SHA-256 digests of the prepared databases. A new generation or a server restart requires a full lookup again
- **Indexed lookups**: later lookups in the same server process read only the matching records. Each lookup still checks the manifest, the age of every database and the SHA-256 of every private ZIP copy. Each record read is checked for length, CRC, UTF-8 and identity. Results, ordering, deduplication and limits are the same as a full lookup. IDs with conflicting copies and lookups with non-default limits use the full lookup
- **Measured on the complete official npm database** (macOS arm64, Node.js 26.12.1, network denied): later lookups took 0.38–0.70 seconds instead of 24.8–32.1 seconds (medians of 3). All ten paired responses were equal to the previous version, and all eight expiry and corruption checks were refused. See `docs/OFFLINE_NPM_VALIDATION.md`, "Indexed explanation comparison"
- **Memory**: the index stays in the server process. By a synthetic estimate it uses about 46–85 MiB for an index shaped like the complete npm database, and at most about 190 MiB within the default limits. Up to two indexes can exist briefly while a new generation is indexed. See "Index memory" in the same document
- **Timeouts**: the lookup deadline now also covers waiting for the ZIP to close and for the private copy to be removed. On expiry the lookup returns `scan_timeout` and releases its scan slot. A partially built index is discarded

Online behavior, `suggest_fix`, scanning and the pinned OSV-Scanner 2.7.0 are unchanged from v0.24.3.

## Development

- `scripts/compare-offline-explain-index.mjs` compares response bodies and timings of two builds on one official npm database under OS-enforced network denial. Interrupted runs are saved as `failed` with a new run ID
- `scripts/measure-offline-index-memory.mjs` reproduces the synthetic index memory estimate
- Research validation records in `docs/validation` bind the exact `package.json` and `package-lock.json` bytes they were measured with. The version bump in this release makes them differ at HEAD again, as described for v0.23.0

## Verification

- Automated tests (product scope: 3,202 passed), type check and build, including regression tests for indexed alias and miss lookups, generation changes, match limits, and deadlines while ZIP closure or private-copy removal is pending
- Dependency audit: `npm audit` and OSV-Scanner 2.7.0 on `package-lock.json` report no findings

npm publication is separate from this GitHub release.
