# v0.18.0

## .NET (NuGet) support in `suggest_fix`

`suggest_fix` now recommends upgrade versions for NuGet packages found by `scan_project` (from `packages.lock.json`, `obj/project.assets.json`, `packages.config`, `*.deps.json`, and project files). Until v0.17.0, NuGet packages were returned with `verification: "unsupported_ecosystem"`.

**NuGet version ordering.** Versions are compared as NuGet does (its VersionRelease ordering, not strict SemVer):

- One to four numeric components, with missing components treated as zero (`1.0` = `1.0.0` = `1.0.0.0`), including the fourth "revision" component (`4.3.0` < `4.3.0.1`). Numeric components must fit a nonnegative 32-bit integer
- Prerelease labels are compared without regard to case (`-Alpha` = `-alpha`). Numeric labels are compared as numbers (`rc.2` < `rc.10`), other labels lexically (`alpha10` < `alpha2`, as in NuGet's documentation), and a numeric label sorts before a non-numeric one. Numeric labels with leading zeroes are rejected
- Build metadata (`+abc`) does not affect ordering. Package IDs are matched without regard to case
- `fixed_versions` for NuGet packages are now sorted in this order

The ordering reproduces the SemVer 2.0 sorting example in NuGet's documentation. Formats that cannot be parsed, and advisories whose version boundaries cannot be compared, do not produce a verified recommendation. The existing three-tier recommendation and the OSV recheck of the candidate (`candidate_check`) apply, and the cautious 0.x rules are the same as for other ecosystems.

**Update hints** depend on the package:

- Direct dependencies: update the `PackageReference` (or `packages.config` in older projects); with central package management, update `PackageVersion` in `Directory.Packages.props`
- Transitive dependencies: update the parent dependency, or reference a compatible fixed version explicitly where NuGet's resolution allows it
- Runtime packs (`Microsoft.NETCore.App.Runtime.*`, `Microsoft.AspNetCore.App.Runtime.*`, `Microsoft.WindowsDesktop.App.Runtime.*`): update the .NET SDK, runtime, or target framework rather than adding a package reference

**Lower bounds.** A package scanned from a project file's `Version="x"` or an inclusive minimum range keeps `version_is_lower_bound: true` in its suggestion, and the note says that the recommendation means raising the `PackageReference` lower bound (previously the note referred to `requirements.txt` only). The flag is now also kept when no recommendation can be made.

Recommendations are not edits: `dotnet restore` and MSBuild are not run. Neither a verified recommendation nor `candidate_check: "clean"` proves target-framework or RID compatibility, availability on a private feed, or the absence of unknown vulnerabilities. Regenerate the restore outputs or lockfiles in a trusted environment and scan again.

Checked through MCP with the real OSV-Scanner 2.7.0: for example `Newtonsoft.Json` 12.0.1 → 13.0.1, `System.Net.Http` 4.3.0 → 4.3.4, and the runtime pack `Microsoft.NETCore.App.Runtime.linux-x64` 8.0.0 → 8.0.32, each `verified` with `candidate_check: "clean"`.

## Verification

- Automated tests (1045), type check, and build
- Through MCP with the real OSV-Scanner 2.7.0: lockfiles, `project.assets.json`, `packages.config`, `*.deps.json` (including a runtime pack), project files with only direct references (lower bounds), and malformed XML alongside other files
- Dependency audit (`npm audit` and OSV-Scanner): no findings; dependencies are unchanged since v0.17.0
