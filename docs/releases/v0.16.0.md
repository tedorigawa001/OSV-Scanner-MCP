# v0.16.0

## .NET (NuGet) support in `scan_project`

`scan_project` now scans .NET projects. Supported files are `packages.lock.json` (and `packages.<project>.lock.json`), `obj/project.assets.json`, `packages.config` (and `packages.<project>.config`), `*.deps.json`, and the `PackageReference` items of `*.csproj` / `*.fsproj` / `*.vbproj` files. Neither `dotnet restore` nor MSBuild is run, and project files are never evaluated.

**No .NET file is passed to OSV-Scanner as it is.** OSV-Scanner 2.7.0 looks up the project's own projects in `*.deps.json` as NuGet packages (a false positive when the name matches a public package, and internal names are sent to `api.osv.dev`), and it passes `.csproj` versions such as `$(Version)` or `[1.0,2.0)` to OSV as they are. OSV treats a version it cannot parse as older than every release, so every known vulnerability of the package was reported. The server parses each file and scans a private copy, in `packages.lock.json` format, that lists only packages with a known version.

- **Matching per project file.** Each project uses the first source confirmed to belong to it: `packages.<project>.lock.json`; `packages.lock.json` only when the directory has a single project file; `packages.config` under the same rule; then `obj/project.assets.json` only when its recorded `projectPath` names this project (projects in one directory share `obj`). A project that sets `NuGetLockFilePath` is not matched to a default-named lockfile. A lockfile that cannot be matched is still scanned, but no project counts as covered by it
- **Projects without a matching source** are scanned from their direct `PackageReference` items only and listed in `lockfile_missing` with `status: "direct_only"` (or `"unconfirmed"`), so `complete` is `false`. This includes projects without any `PackageReference` of their own, since `Directory.Build.props` or the SDK can add references
- **`PackageReference` versions.** `[x]` is looked up as x. `x`, `[x,)`, and `[x,y)` mean x or higher (NuGet restores the lowest available version, which may be above x), so they are looked up at x and marked `version_is_lower_bound: true`. Ranges without an included lower bound, `$(...)`, floating versions (`*`), and missing versions (central package management) are not looked up
- **References that might not apply are not looked up**: conditions on the reference, its `ItemGroup`, or its `Version`; references inside `Choose` or `Target`; names that also have `Update` or `Remove` in the file or in a `Directory.Build.props` / `Directory.Build.targets` in the scanned directory; duplicates; and `VersionOverride`. They are listed with the reason in the new `coverage.unresolved_package_references`
- **Restore results.** The project's own projects (`type: project` and so on) are counted in `coverage.local_projects` and not looked up. Runtime packs of self-contained apps in `*.deps.json` are looked up under their package names (the SDK writes them as `runtimepack.<name>`, which OSV does not match). Entries of an unknown type or without a plain version are listed in `coverage.unscannable_nuget_packages`
- `bin` and `obj` in a directory that contains a project file are not searched (they hold that project's build output)
- `coverage.nuget_warnings` notes lower bounds, a `project.assets.json` that is more than a minute older than its project file, references that cannot be checked from project files alone, and package sources other than nuget.org in a `nuget.config`
- **Private NuGet feeds.** Lockfiles do not record which feed a package came from, so the names of packages from private feeds are sent to `api.osv.dev` as well. This is documented in the README and SECURITY.md
- Direct and transitive dependencies are shown from `packages.lock.json`, `project.assets.json`, `*.deps.json`, and project files (`packages.config` is `unknown`). `suggest_fix` does not support NuGet yet and returns `verification: "unsupported_ecosystem"`

Limits: project files, `packages.config`, and `nuget.config` are read by a small XML parser that rejects `DOCTYPE`, entity declarations, and CDATA (4 MiB per file). JSON files use the same structural checks as npm lockfiles (16 MiB per file). Per scan, at most 10,000 .NET files are examined, and up to 1,000 of them and 200,000 packages are scanned; files beyond that are listed in `skipped_files`.

The behavior was checked against real files from public repositories (Project-MONAI/monai-deploy-informatics-gateway, EasyPost/easypost-csharp, Tophness/StickyMouse, bitmono-project/BitMono): the packages scanned are exactly the ones OSV-Scanner reads from the original files, minus the projects' own code.

## Opened-file boundary verification (affects `--permission` users)

Reads that are limited to the scan scope (`OSV_MCP_ALLOWED_ROOT`, the project directory, parent POMs, and SBOMs) now confirm the location of the file through the handle that is still open, using the path the operating system reports for it: `/proc/self/fd` on Linux, `F_GETPATH` on macOS, and `GetFinalPathNameByHandleW` on Windows. Previously the path was resolved again by name after reading, which a directory renamed at the right moment could make look as if it were inside the scope. If the location cannot be confirmed, the file is not read.

On macOS and Windows this uses the native binding [koffi](https://github.com/Koromix/koffi) (3.3.3, with prebuilt binaries installed as optional per-platform packages). **If you run the server under Node's permission model, add `--allow-addons` on macOS and Windows, or `--allow-fs-read=/proc/self/fd` on Linux.** Without it, the server warns at startup, and files whose location cannot be confirmed are not read: `scan_project` and the other project scans list them in `skipped_files` with the reason (so `complete` is `false`), and `scan_sbom` returns `permission_denied`. Native code runs outside Node's permission sandbox; keep OS-level isolation if you need stronger isolation. The check runs on Linux, macOS, and Windows in CI.

## Fix: An invalid character reference could stop the whole scan (v0.4.0–v0.15.0)

An XML character reference outside Unicode or in the surrogate range (for example `&#x110000;`) made the decoder throw, so a single `pom.xml` with such a reference in its parent `relativePath` made the whole `scan_project` / `scan_java_project` / `suggest_fix` call fail with `internal_error`, and the results for every other ecosystem in the project were lost. A repository could prevent itself from being scanned with one file. Such a file is now treated as uninterpretable and listed in `skipped_files` with the reason, and the rest of the project is scanned. Named entity references are also matched against the five predefined entities only (`&constructor;` and similar names no longer expand to object properties).

## Other Changes

- Linear-time parsing of XML attributes (an unanchored regular expression retried failed whitespace from every offset) and of the direct dependencies in `*.deps.json`, and work limits for matching .NET projects
- `body-parser` 2.4.0 (GHSA-27r3-jxmh-p828) and `fast-uri` 3.1.9 in the lockfile. Both are dependencies of the MCP SDK; `body-parser` is used only by its HTTP server, which this server does not use. Installs from npm already resolve the fixed versions
- The package description and keywords list all supported ecosystems
