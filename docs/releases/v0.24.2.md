# v0.24.2

## Security Fixes

Affected versions: v0.24.1 and earlier. These are low-severity hardening fixes found in the same code review as v0.24.1. Fixed in v0.24.2.

### An unreadable directory was skipped without being reported

The manifest search skipped directories that could not be read, for example because of missing permissions, and did not report them. Their manifests were missing from the scan while `coverage.complete` stayed `true`. A project unpacked from an archive with a mode-000 directory containing a vulnerable lockfile was reported as fully covered with no findings.

- `scan_project` now lists such directories in `skipped_files` with a reason, so `complete` is `false` and the coverage warning is shown
- `scan_java_project` lists them in `skipped_manifests`
- When no manifest is found, the error reason includes them. Denials by the Node permission model are still errors, as before

### A single huge directory was read into memory before the entry limit was checked

A directory with millions of entries was listed in full before the 200,000-entry limit applied. Entries are now read one by one and the limit is checked while reading. The order of detected manifests is unchanged.

### Long advisory strings were returned in full

Only `summary` and `details` were length-limited. One crafted OSV record could return megabytes of text in fields that look like identifiers.

- `explain_vulnerability` limits aliases, package names, ecosystems, versions, dates, CVSS values and reference types to 256 characters
- Reference URLs longer than 2,048 characters are dropped, not truncated, because a truncated URL can point elsewhere
- A record `id` that does not match the OSV ID format is replaced by the requested ID. This check was previously applied only offline
- In `suggest_fix`, `recommended_known_vulnerabilities` and the IDs listed in `upgrade_note` are limited to 20 IDs of 128 characters, with the remaining count shown as `(N more)`. Fixed versions longer than 256 characters are not used as candidates

### Some invisible characters were not removed from external text

Variation selectors (U+FE00–U+FE0F and U+E0100–U+E01EF) can invisibly encode arbitrary bytes after a visible character. They are now removed, along with invisible fillers (U+034F, U+115F, U+1160, U+3164, U+FFA0) and interlinear annotation characters (U+FFF9–U+FFFB).

### Relative PATH entries were searched for osv-scanner

A relative `PATH` entry such as `.` resolves against the server's working directory, so an `osv-scanner` placed there could run. Relative entries are now ignored. Absolute entries, `OSV_SCANNER_PATH` and `OSV_MCP_PREFER_DOWNLOAD` behave as before.

## Behavior Changes

- Coverage can now be incomplete in projects with unreadable directories that were previously reported as complete
- Emoji in advisory text may be shown in text style, because the emoji presentation selector U+FE0F is removed

Scanning behavior, responses and the pinned OSV-Scanner 2.7.0 are otherwise unchanged from v0.24.1.

## Development

- GitHub Actions in CI are pinned to commit SHAs instead of tags, and Dependabot now also updates GitHub Actions
- Research validation records in `docs/validation` bind the exact `package.json` and `package-lock.json` bytes they were measured with. The version bump in this release makes them differ at HEAD again, as described for v0.23.0

## Verification

- Automated tests (product scope: 3,189 passed), type check and build, including new tests for unreadable directories, streamed directory reads, crafted advisory records, invisible characters and relative PATH entries. The unreadable-directory tests are skipped when running as root or on Windows
- Dependency audit: `npm audit` and OSV-Scanner 2.7.0 on `package-lock.json` report no findings
- GitHub Actions passed on Node.js 22, 24 and 26 on Linux, macOS and Windows, including the OSV-Scanner job

npm publication is separate from this GitHub release.
